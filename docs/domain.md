# 도메인 뼈대

과제의 기본 운영 스키마. 개발 시 이 문서를 기준으로 하고, 여기에 없는 내용은 임의로 정하지 않고 확인한다.

## 구조

```
호텔
 ├─ 호텔 정보
 └─ 객실 (여러 개)
      ├─ 객실 정보
      ├─ 객실 상태
      └─ 이용 (여러 번)
           ├─ 이용 기간
           ├─ 이용객 ──→ 이용객 정보 (별도)
           └─ 취소 기록
```

## 호텔

| 항목 | 필수 | 최대 길이 | 규칙 |
|---|---|---|---|
| 이름 | 필수 | 100자 | |
| 주소 | 필수 | 200자 | 한 줄 문자열 |
| 대표 전화번호 | 필수 | 20자 | 숫자와 `-`만, 숫자는 8~11개. 입력한 모양 그대로 저장한다 |
| 소개 | 선택 | 1000자 | 비어 있으면 저장하지 않는다(null) |

- 값은 앞뒤 공백을 지우고 저장한다. 공백만 있는 값은 빈 값으로 본다.
- 호텔은 id로 구분한다. 이름은 같아도 된다.
- 이름과 주소가 모두 같은 호텔은 같은 호텔로 보고 등록·수정을 거절한다(409). 앞뒤 공백을 지운 값을 글자 그대로 비교한다(대소문자 구분).
  - DB 유일 제약으로도 막아, 같은 등록 요청이 동시에 두 번 와도 먼저 저장된 하나만 남는다.
- 여러 사람이 같은 호텔을 동시에 수정하면, 나중에 저장한 쪽은 먼저 저장된 변경을 모른 채 덮어쓰지 않도록 거절한다(409). 조회할 때 받은 버전(version)을 수정 요청에 함께 보낸다.
- 호텔 목록은 이름으로 검색할 수 있다. 이름에 검색어가 들어 있는 호텔을 찾는다(대소문자 구분 없음).
- 체크인·체크아웃 시각은 호텔이 아니라 객실마다 둔다.
- 호텔 삭제는 아직 다루지 않는다.

## 객실 상태

공실 → 예약됨 → 이용중 → 정비중 → 공실

| 상태 | 의미 |
|---|---|
| 공실 | 이용 가능한 빈 객실 |
| 예약됨 | 운영자가 객실을 확인하고 예약을 허용한 상태 |
| 이용중 | 이용객이 입실해 이용 중인 상태 |
| 정비중 | 퇴실 후 공실이 되기 전까지 청소·수리 중인 상태 |

- 상태 변경은 운영자가 수동으로 한다. 자동 변경은 범위 밖이다.
- 단, 이용이 취소되면 객실 상태는 자동으로 공실이 된다.
- 투숙 중 청소는 객실 상태가 아니라 별도 운영 도메인에서 다룬다.

## 이용

- 이용은 이용 기간과 이용객을 하나로 묶은 단위다. 객실은 여러 번의 이용을 가진다.
- 같은 객실에 기간이 겹치는 이용은 등록할 수 없다. 서버에서 막고, 클라이언트에서도 검증한다.
- 취소하면 이용객이 취소했다는 기록을 남긴다.

## 이용객

- 이용과 분리해 둔다. 같은 이용객이 여러 번 이용할 수 있다.
- 추후 이용객이 앱에 접근할 때 계정(id)과 연결할 수 있도록 확장을 고려한다.

## 운영 계정과 역할

| 역할 | 앱 | 하는 일 |
|---|---|---|
| 전체 어드민 | app-admin | 호텔 등록·수정, 앱 설정(호텔 마스터 계정 관리, 게스트 앱 노출 설정) |
| 호텔 마스터 | hotel-admin | 호텔 운영자 업무 전부 + 같은 호텔의 운영자 계정 관리 |
| 호텔 운영자 | hotel-admin | 자기 호텔의 정보 수정, 객실 등록·수정, 객실 상태 변경, 이용·이용객 관리 |

- 두 어드민 앱은 계정으로 로그인한다. 어드민 계정과 호텔 계정(마스터·운영자)은 따로 저장한다.
- 전체 어드민
  - 계정 항목은 아이디(이메일), 비밀번호, 이름이다. 아이디는 대소문자와 앞뒤 공백을 구분하지 않는다.
  - 첫 계정은 백엔드가 뜰 때 설정값으로 만든다. 어드민이 하나도 없을 때만 만든다.
  - 어드민은 다른 어드민 계정을 추가할 수 있다.
  - 호텔 계정 중 마스터 계정만 관리한다.
- 호텔 마스터는 어드민이 호텔을 만들 때 함께 발급한다. 호텔마다 하나다.
- 호텔 운영자는 마스터가 만든다. 한 호텔에 여러 명 둘 수 있다.
- 호텔 계정은 자기 호텔만 다룬다.

## 미정

- 객실 정보 / 이용객 정보의 세부 항목 (객실에는 체크인·체크아웃 시각이 들어간다)
- 운영 측면(별도 운영 도메인) — 뼈대 완성 후 논의
- 호텔 계정(마스터·운영자)의 세부 항목, 마스터와 운영자를 구분하는 방식
- 비밀번호 규칙(길이·조합). 계정을 추가하는 API를 만들 때 정한다.
- 계정을 지우거나 바꿨을 때 이미 로그인한 세션을 끊을지
- 앱 설정(게스트 앱 노출 설정)의 세부 내용
- 게스트 앱의 로그인
