# handys-urbanstay

여러 호텔을 운영하는 숙박 운영사의 운영 도구와 게스트 예약 화면이다. 게스트는 게스트 앱에서 객실 유형을 골라 예약하고, 호텔 운영자는 hotel-admin에서 객실과 예약을 관리한다. 객실 중복 배정, 객실 상태 꼬임, 이용 취소 누락을 서버 규칙으로 막는 데 집중했다.

| 구성 | 위치 | 사용자 | 기술 |
|---|---|---|---|
| 백엔드 API | `backend` | 세 앱 | Kotlin 2.3, Spring Boot 4.1, PostgreSQL 18, Flyway |
| 전체 어드민 앱 | `frontend/apps/app-admin` | 운영사 어드민 | Vite + React, TanStack Router·Query |
| 호텔 운영자 앱 | `frontend/apps/hotel-admin` | 호텔 마스터·운영자 | Vite + React, TanStack Router·Query |
| 게스트 앱 | `frontend/apps/web` | 게스트 (로그인 없이 예약) | Next.js 16 |

## 1. 문제 정의

운영사 한 곳이 여러 호텔을 운영한다고 가정한다. 운영사의 전체 어드민이 호텔을 등록한다. 게스트는 게스트 앱에서 로그인 없이 객실 유형을 골라 예약하고(객실은 서버가 배정한다), 각 호텔의 마스터·운영자는 자기 호텔의 객실과 객실 상태를 관리하면서 들어온 이용(예약)을 확인·취소한다.

| 문제 | 그대로 두면 | 지켜야 할 규칙 |
|---|---|---|
| 중복 배정 | 같은 객실에 기간이 겹치는 이용이 두 건 저장되어, 한 방에 두 팀이 배정된다 | 같은 객실에 기간이 겹치는 이용은 하나만 둔다. 게스트는 유형으로 예약하고 서버가 객실을 배정하므로, 같은 유형에 예약이 동시에 와도 한 객실에 겹치는 이용이 생기지 않아야 한다. 그사이 빈 객실이 없어졌으면 거절한다 |
| 객실 상태 꼬임 | 허용되지 않는 변경(예: 공실 → 이용중)이나 동시 변경 충돌로 실제와 다른 상태가 된다 | 정해진 방향으로만 바꾼다. 화면에서 본 상태가 그대로일 때만 바꾼다. 누가 언제 바꿨는지 남긴다 |
| 취소 처리 | 기록 없이 사라지거나, 두 번 처리되거나, 객실 상태가 그대로 남는다 | 취소 기록(누가·언제·왜)과 객실 상태 복구가 함께, 한 번만 일어난다 |
| 계정·권한 | 다른 호텔의 데이터를 보거나 바꾼다 | 역할별로 할 수 있는 일을 나누고, 호텔 계정은 자기 호텔만 다룬다 |

### 객실 상태

```mermaid
stateDiagram-v2
    state "공실" as VACANT
    state "예약됨" as RESERVED
    state "이용중" as OCCUPIED
    state "정비중" as MAINTENANCE
    [*] --> VACANT: 객실 등록
    VACANT --> RESERVED
    RESERVED --> OCCUPIED
    OCCUPIED --> MAINTENANCE
    MAINTENANCE --> VACANT
    RESERVED --> VACANT: 예약 되돌림
    VACANT --> MAINTENANCE: 이용 없이 정비
```

- 위 여섯 방향만 허용한다. 그 밖의 변경과 같은 상태로 바꾸는 요청은 거절한다.
- 상태는 운영자가 직접 바꾼다. 예약은 객실 상태와 관계없이 할 수 있고, 객실 상태를 바꾸지 않는다.
- 예외는 하나다. 이용을 취소할 때 객실이 예약됨이면 공실로 돌린다. 이용중·정비중이면 그대로 둔다. 다른 이용객이 쓰는 객실이 다른 이용의 취소로 공실이 되지 않게 하기 위해서다.

### 이용과 예약

- 이용은 객실, 이용객, 기간, 인원을 묶은 단위다. 기간은 날짜 단위(박)이고 체크아웃 날은 비어 있다고 본다(1일~3일과 3일~5일은 겹치지 않는다).
- 체크인은 오늘(한국 시간) 이후, 1~30박, 인원은 객실 최대 인원 이하다.
- 이용(예약)은 게스트 앱에서 이용객이 한다. 호텔 → 날짜·인원 → 객실 유형 → 이름·전화번호·이메일 순서다.
- 객실 유형은 같은 호텔에서 '객실 유형' 값이 같은 객실들이다(예: 유형이 '스위트룸'인 객실이 2개면 '스위트룸 2'). 날짜·인원을 고르면 유형마다 그 기간·인원으로 예약할 수 있는 객실 수를 보여주고, 0이면 '예약불가'로 고를 수 없다.
  - 예약할 수 있는 객실: 그 유형이고, 최대 인원이 인원 이상이고, 그 기간에 취소하지 않은 이용과 겹치지 않는 객실. 객실 상태와는 관계없다.
- 게스트는 객실(호수)을 고르지 않는다. 서버가 예약할 수 있는 객실 중 객실 이름순 첫 객실을 배정한다. 완료 화면에도 호수는 보여주지 않는다.
- 이용객은 호텔마다 따로 둔다. 예약 요청 하나로 이용객과 이용을 함께 저장하고, 함께 성공하거나 함께 실패한다. 같은 호텔에 전화번호(숫자만 비교)가 같은 이용객이 있으면 그 이용객으로 예약하고 이름·이메일은 바꾸지 않는다.
- hotel-admin은 자기 호텔의 이용을 조회·취소하고, 이용객을 조회·수정한다. 등록은 하지 않는다.
- hotel-admin 객실 목록·상세는 그 객실의 지금 이용(오늘(한국 시간)이 기간 안인 취소하지 않은 이용)과 이용객을 보여준다. 객실 상태는 지금 이용과 따로, 운영자가 바꾼다.
- 이용은 수정하지 않는다. 바꾸려면 취소하고 다시 예약한다. 취소한 이용은 겹침 검사에서 뺀다.
- 끝나지 않은 이용만 취소할 수 있고, 취소는 되돌릴 수 없다.

### 계정과 역할

| 역할 | 앱 | 하는 일 |
|---|---|---|
| 전체 어드민 | app-admin | 호텔 등록·수정, 호텔 마스터 계정 관리 |
| 호텔 마스터 | hotel-admin | 운영자 업무 전부 + 같은 호텔의 운영자 계정 관리 |
| 호텔 운영자 | hotel-admin | 자기 호텔의 정보 수정, 객실 등록·수정, 객실 상태 변경, 이용 조회·취소, 이용객 조회·수정 |

- 게스트는 계정 없이(로그인 없이) 게스트 앱에서 예약한다. 예약하면서 그 호텔의 이용객으로 등록된다.
- 호텔 마스터는 어드민이 호텔을 등록할 때 함께 만들어진다(호텔마다 하나). 운영자는 마스터가 만들고, 지우지 않고 비활성화한다.
- 계정이 비활성화되거나 비밀번호·아이디가 바뀌면 그 계정의 기존 세션은 다음 요청에서 끊긴다.

전체 규칙은 [docs/domain.md](docs/domain.md)에 있다.

## 2. 해결 방식

규칙마다 서버가 어떻게 지키는지 정리했다. 화면에서 막는 것은 보조이고, 최종 판단은 서버와 DB가 한다.

| 규칙 | 서버가 지키는 방법 | 실패 응답 |
|---|---|---|
| 기간 겹침 금지 | PostgreSQL 배제 제약(`exclude using gist`, `daterange [)`, 취소하지 않은 이용만)이 마지막 안전망이다. 예약은 아래 행처럼 잠근 뒤 겹치지 않는 객실만 고른다 | 409 `STAY_PERIOD_OVERLAPPED` |
| 같은 유형 동시 예약 | 그 호텔·유형의 객실 행을 id 오름차순으로 비관적 잠금(`@Lock(PESSIMISTIC_WRITE)`, PostgreSQL에서 `for no key update`)한 뒤, 다음 문장에서 겹치는 이용을 다시 조회해 예약할 수 있는 객실 중 이름순 첫 객실을 배정한다. 같은 유형 예약은 한 건씩 처리되고, 다른 유형 예약은 서로 기다리지 않는다. 확인만 하고 고르면 동시에 온 두 요청이 같은 객실을 고른다. 잠금을 거치지 않은 이용 INSERT는 배제 제약이 막는다 | 409 `ROOM_TYPE_UNAVAILABLE` (빈 객실 없음) |
| 예약불가 계산 | 유형 목록과 예약이 같은 계산(`StayService.availableRooms`)을 쓴다. 호텔 객실을 유형순으로 한 번 읽고, 겹치는 객실 id를 한 번에 찾아 유형별로 묶는다. `availableCount`가 0이면 화면이 '예약불가'로 보여주고 고를 수 없게 한다 | - |
| 같은 새 이용객의 동시 예약 | 예약 한 건을 한 트랜잭션으로 처리한다. 같은 호텔·같은 전화번호의 이용객을 먼저 찾고, 없으면 `insert ... on conflict do nothing` 뒤 다시 조회한다. 동시에 온 두 예약도 이용객은 하나다. 배정·저장이 실패하면(빈 객실 없음, 겹침) 함께 넣은 이용객도 남지 않는다 | - |
| 객실 상태 전이 | 상태 전이 표(`RoomStatus.canChangeTo`). 16가지 조합 전부를 테스트한다 | 409 `ROOM_STATUS_TRANSITION_NOT_ALLOWED` |
| 동시 상태 변경 | 화면에서 본 상태(`from`)를 함께 받아 조건부 UPDATE(`where status = :from`). 바뀐 행이 없으면 먼저 바뀐 것이다 | 409 `ROOM_STATUS_CHANGED` |
| 상태 이력 | 상태 변경과 같은 트랜잭션에서 한 줄 저장. 이전·바뀐 상태, 계정 id와 그때의 이름, 시각 | - |
| 취소는 한 번만 | 조건부 UPDATE(`where canceled_at is null`). 같은 트랜잭션에서 객실 `RESERVED → VACANT` 조건부 UPDATE와 이력 저장 | 409 `STAY_ALREADY_CANCELED` |
| 동시 수정 | 낙관적 잠금(`@Version`). 수정 요청에 조회 때 받은 `version`을 보낸다. 호텔·객실·이용객·호텔 계정 | 409 `*_MODIFIED` |
| 중복 등록 | 사전 확인 + DB 유일 제약. 위반을 도메인 409로 바꾼다. 호텔 이름+주소, 같은 호텔의 객실 이름, 같은 호텔의 이용객 전화번호(숫자만 비교, 수정 때), 호텔 계정 아이디, 호텔당 마스터 하나 | 409 |
| 자기 호텔만 | 호텔 id는 요청이 아니라 로그인한 세션의 계정에서 읽는다. 다른 호텔의 데이터는 없는 것으로 다룬다 | 404 |
| 로그인·권한 | 서버 세션 + HttpOnly 쿠키. 어드민 API의 변경 요청은 CSRF 토큰(`XSRF-TOKEN` 쿠키 → `X-XSRF-TOKEN` 헤더). 요청마다 호텔 계정을 다시 확인해 바뀐 계정의 세션을 끊는다 | 401 / 403 |
| 앱별 정책 | API 경로, 컨트롤러·DTO, API 문서 그룹을 앱별로 나눈다(`/api/v1/app`, `/api/v1/app-admin`, `/api/v1/hotel-admin`). 게스트 앱 API(`/api/v1/app`)는 로그인·CSRF 없이 쓴다 | - |
| 응답 형식 | 모든 응답을 `{ success, data, message, error }`로 감싼다. 성공 문구와 오류 문구는 서버가 정하고, 화면은 받은 문구를 그대로 보여준다 | - |
| 입력 검증 | 서버는 Bean Validation과 서비스 검사, 클라이언트는 orval이 만든 zod로 요청과 응답을 모두 검증한다 | 400 `INVALID_INPUT` + `fieldErrors` |

객실 상태는 `version`과 따로 움직인다. 상태가 바뀌어도 열어 둔 객실 수정은 거절되지 않고, 반대로 객실 수정이 상태를 옛 값으로 덮어쓰지 않도록 `Room.status`를 JPA UPDATE에서 뺐다(`@Column(updatable = false)`).

이용객을 만들 때 JPA 저장 뒤 유일 위반을 바꾸는 방식을 쓰지 않은 것은, PostgreSQL에서 오류가 난 트랜잭션은 이어서 이용을 저장할 수 없기 때문이다. 기존 유일 인덱스 하나로 막고, advisory lock은 쓰지 않았다(#91).

### 검증

- DB가 필요한 백엔드 테스트는 실제 PostgreSQL(Testcontainers)에서 돈다. 백엔드 테스트는 PR #97 시점에 1203개다.
- 동시성은 두 가지로 확인한다.
  - 동시 요청: 두 스레드를 함께 출발시킨다. 실행마다 어느 경로를 탈지 정해지지 않는다.
  - 순서 고정: 먼저 온 트랜잭션을 열어 둔 채 다음 요청이 잠금을 기다리는지 확인하고 커밋한다. "사전 확인은 통과했지만 DB에서 막히는" 경로를 매번 같게 재현한다.
  - 객실 유형 예약은 같은 유형의 다음 예약이 객실 잠금을 기다렸다가 다음 이름순 객실을 받는 경로, 빈 객실이 없어 `ROOM_TYPE_UNAVAILABLE`이 되는 경로, 잠금을 거치지 않은 겹치는 이용을 배제 제약이 막는 경로를 확인한다(`StayServiceTest`).
- 실제 서버를 띄워 요청을 보내 확인한 항목은 PR 본문에 적었다(예: #49, #55, #58).

### 등록 주체 변경: 이용객·이용은 게스트 앱에서

- 처음 규칙(#75)은 호텔 계정이 hotel-admin에서 이용객과 이용을 등록하는 것이었다. 백엔드 API(#76, #78)와 hotel-admin 이용객 등록 화면(#85)까지 만들었다.
- hotel-admin 이용 화면을 만들던 중 사용자가 '이용객은 게스트 앱에서 예약하면서 등록한다'고 바로잡았다(#87). 게스트가 예약하고, 호텔은 들어온 예약을 조회·취소한다.
- hotel-admin의 이용객·이용 등록 API와 이용객 등록 화면을 지우고(#91, #92), 게스트 앱 API 4개(호텔 목록, 호텔의 객실 목록, 객실의 예약된 기간, 예약)를 만들었다(#91).
- 등록 API 제거와 게스트 앱 API는 한 PR(#91)에 두었다. 제거만 먼저 병합하면 이용을 등록할 길이 없는 상태가 생기기 때문이다.
- 남은 한계
  - 로그인이 없어 다른 사람의 전화번호로 예약할 수 있다. 게스트 앱 로그인을 정할 때 함께 다룬다(#87).
  - 예약에 보낸 이름·이메일이 기존 이용객과 달라도 따로 알리지 않는다. 응답에 기존 이름이 나올 뿐이다(#91).
  - 새 이용객 INSERT가 기존 행과 부딪힌 뒤 다시 찾기 전에 그 이용객의 전화번호가 수정되어 커밋되면 500이 된다. 아주 드물어 다루지 않았다(#91).

### 객실 유형 예약으로 변경 (#93)

- 게스트 앱 예약 화면(호텔 → 객실 → 날짜·인원, 예약된 기간 표시)을 만들던 중 사용자가 객실 정보를 다시 정리했다. 호텔에는 여러 유형의 객실이 있고(예: 스위트룸 2, 한강뷰 스위트룸 3), 게스트는 유형을 골라 예약하며, 유형의 객실이 모두 차면 '예약불가'다. 호텔은 객실의 지금 이용객도 본다.
- 진행 중이던 게스트 앱 객실 선택 화면을 멈추고 문서(#93) → 백엔드(지금 이용 #95, 객실 유형 예약 #97) → 프론트엔드(hotel-admin 지금 이용객 #96, 게스트 앱 예약 화면 #98) 순서로 다시 맞췄다.
- 게스트 앱 API: 객실 목록·예약된 기간 API를 지우고 객실 유형 목록(`GET /api/v1/app/hotels/{hotelId}/room-types`)을 두었다. 예약(`POST /api/v1/app/stays`)은 객실 id 대신 `hotelId`·`roomType`을 받고, 응답에 배정한 객실을 싣지 않는다.
- 사용자 결정: 서버가 빈 객실을 자동 배정, 고른 기간 기준 '예약불가', 객실에 지금 이용객 표시(상태는 수동), 객실 유형은 별도 표 없이 객실의 유형 값으로 묶는다(지금 구조 유지). 배정 순서(객실 이름순 첫 객실)는 메인 에이전트가 정했다.
- 남은 한계
  - 같은 유형인데 최대 인원·체크인 시각이 객실마다 다를 수 있다(#93).
  - 지금 이용과 객실 상태는 따로 정해진다. 상태가 '공실'인데 지금 이용객이 보일 수 있다(#96).

### 하지 않은 것

| 항목 | 이유 |
|---|---|
| 객실 상태 자동 변경(날짜에 따라 이용중 등) | 도메인 문서에서 범위 밖으로 정했다. 상태는 운영자가 바꾸고, 예외는 취소 때 예약됨 → 공실 하나다 |
| 이용 수정 | 도메인 문서에서 취소 후 다시 예약하는 규칙으로 정했다 |
| 결제·요금 | 도메인 뼈대에 없다. 배정·상태·취소의 정합성에 집중했다 |
| 객실 유형을 따로 관리하는 표(유형별 요금·사진 등) | 객실 유형은 객실의 '객실 유형' 값으로 묶는다(사용자 결정: 지금 구조 유지, #93) |
| 객실 배정 규칙(청소 상태, 층 등) | 객실 이름순 첫 빈 객실을 배정한다(#93) |
| 체크인·체크아웃 시각까지 반영한 '지금 이용' 판정 | 날짜 단위로 판정한다. 체크아웃 날에는 체크아웃 시각 전이어도 지금 이용이 없고, 체크인 날에는 체크인 시각 전이어도 지금 이용으로 보인다(#95) |
| 게스트 로그인, 게스트의 예약 조회·취소, 게스트 앱 노출 설정 | 게스트 로그인과 노출 설정은 도메인 문서에서 미정이다(모든 호텔을 보여준다). 게스트의 예약 조회·취소는 범위 밖으로 정했고, 취소는 hotel-admin에서 한다 |
| 본인 비밀번호 변경 | 도메인 문서에서 아직 다루지 않기로 했다 |
| 호텔·객실·이용객 삭제 | 도메인 문서에서 다루지 않기로 했다. 운영자 계정도 지우지 않고 비활성화한다 |
| 전체 어드민 계정 추가 | 도메인 문서에는 있으나 API·화면을 만들지 않았다 |
| hotel-admin의 자기 호텔 정보 수정 | 도메인 문서에는 있으나 API·화면을 만들지 않았다 |
| 별도 운영 도메인(투숙 중 청소 등) | 도메인 문서에서 뼈대 완성 뒤 논의하기로 했다 |
| 배포 환경 | 로컬 실행용이다. CORS는 설정하지 않고, 세션은 서버 메모리에 둔다(백엔드를 다시 띄우면 다시 로그인) |

### 전제와 다른 점: 어드민 앱은 Vite + React SPA

- 과제 전제는 'Frontend: Next.js'다.
- 게스트 앱(`apps/web`)은 Next.js다. 게스트가 로그인 없이 예약하는 화면이다.
- 두 어드민 앱은 로그인한 운영자만 쓰는 화면이다. 검색 노출(SEO)과 서버 렌더링이 필요 없어서 Vite + React SPA(TanStack Router·Query, axios)로 만들었다. 2026-10-28 사용자와 정했다.
- 어드민 앱의 API 호출은 Vite 개발 서버의 proxy가 자기 앱의 API 경로만 백엔드로 넘긴다.

## 4. 실행 방법

### 준비물

| 도구 | 버전 | 근거 |
|---|---|---|
| JDK | 25 | `backend/build.gradle.kts`의 toolchain. Gradle은 wrapper(9.8.2)를 쓴다 |
| Docker Desktop | 실행 중이어야 한다 | 개발 DB(`backend/compose.yaml`)와 테스트(Testcontainers) |
| Node.js | 24에서 확인 | 저장소에 고정한 버전은 없다 |
| pnpm | 10.7.1 | `frontend/package.json`의 `packageManager` |

### 백엔드

```bash
cd backend
./gradlew bootRun          # Windows: .\gradlew.bat bootRun
```

- `compose.yaml`의 PostgreSQL 18 컨테이너가 자동으로 뜬다(Spring Boot Docker Compose). 앱을 꺼도 DB는 계속 떠 있다(`start-only`).
  - 정지: `docker compose stop`, 데이터까지 삭제: `docker compose down -v` (`backend/`에서 실행)
- 스키마는 Flyway가 적용한다(`src/main/resources/db/migration`, V1~V10).
- 주소: `http://localhost:8080`
- Swagger UI: `http://localhost:8080/swagger-ui.html`. 문서는 앱별 그룹이다.
  - `/v3/api-docs/app`, `/v3/api-docs/app-admin`, `/v3/api-docs/hotel-admin`

### 프론트엔드

```bash
cd frontend
pnpm install
pnpm dev                          # 세 앱을 함께 실행 (turbo)
pnpm --filter app-admin dev       # 한 앱만 실행
```

| 앱 | 접속 주소 |
|---|---|
| app-admin | http://app-admin.localhost:5173 |
| hotel-admin | http://hotel-admin.localhost:5174 |
| web | http://localhost:3000 (`next dev` 기본 포트) |

- 백엔드 주소는 각 앱의 `.env.local`(`API_BASE_URL`)에 있고, 과제 제출용으로 커밋했다.
- 어드민 앱은 위의 `*.localhost` 주소로 접속한다. 쿠키는 포트로 나뉘지 않아서, 호스트를 나눠야 두 앱의 세션·CSRF 쿠키가 섞이지 않는다.

### 처음 로그인과 확인 흐름

1. app-admin: 첫 전체 어드민 계정은 백엔드가 뜰 때 `backend/src/main/resources/application.properties`의 `urbanstay.initial-admin.*`(`login-id`, `password`, `name`) 값으로 만들어진다. 어드민이 하나도 없을 때만 만든다. 그 아이디와 비밀번호로 로그인한다.
2. app-admin에서 호텔을 등록한다. 그 호텔의 마스터 계정(아이디, 이름, 처음 비밀번호)을 함께 만든다.
3. hotel-admin에 마스터 계정으로 로그인해 '객실'에서 객실을 등록한다. '객실 유형' 값이 같은 객실이 한 유형이 된다. 운영자 계정은 마스터가 '운영자'에서 만든다.
4. 게스트 앱(`http://localhost:3000`)에서 호텔을 고르고 날짜·인원을 정하면 객실 유형 목록(남은 객실 수, 없으면 '예약불가')이 나온다. 유형을 고르고 이름·전화번호·이메일을 넣어 예약한다. 로그인은 없고, 객실은 서버가 배정한다.
5. hotel-admin '객실' 목록의 '지금 이용객' 열과 객실 상세의 '지금 이용' 카드에서 배정된 객실과 이용객을 확인한다. 체크인을 오늘로 예약하면 바로 보인다.
6. hotel-admin '이용'에서 예약을 확인하고 취소한다. 객실 상태는 객실 상세에서 바꾼다.

```
handys-urbanstay/
├─ CLAUDE.md                     # 작업 지침 (커밋·브랜치·PR 규칙, AI 역할 분담)
├─ docs/                         # 프론트엔드·백엔드 공통 계약
├─ backend/                      # Kotlin + Spring Boot
│  ├─ compose.yaml               # 개발용 PostgreSQL 18
│  └─ src/main/
│     ├─ kotlin/com/marco/assignment/handys/urbanstay/
│     │  ├─ common/              # 응답 봉투, 예외, 보안, 요청 검증, 설정
│     │  ├─ account/             # 전체 어드민·호텔 계정, 로그인
│     │  ├─ hotel/               # 호텔
│     │  ├─ room/                # 객실, 객실 상태와 이력
│     │  ├─ guest/               # 이용객
│     │  └─ stay/                # 이용(예약, 객실 배정), 취소
│     └─ resources/
│        ├─ db/migration/        # Flyway V1~V10
│        └─ messages.properties  # 응답·검증·API 문서 문구
└─ frontend/                     # Turborepo + pnpm workspace
   ├─ apps/
   │  ├─ web/                    # 게스트 앱 (Next.js, 예약 화면)
   │  ├─ app-admin/              # 전체 어드민 앱 (Vite + React)
   │  └─ hotel-admin/            # 호텔 운영자 앱 (Vite + React)
   ├─ packages/
   │  ├─ ui/                     # 두 어드민 앱의 화면 컴포넌트 (@repo/ui)
   │  └─ admin-kit/              # 두 어드민 앱의 도메인 무관 코드 (@repo/admin-kit)

```

- 백엔드 도메인 패키지는 `controller`(앱별 `app`·`appadmin`·`hoteladmin`), `dto`, `service`, `repository`, `entity`, `exception`으로 나눈다. 다른 도메인은 그 도메인의 Service로만 쓴다.
- 프론트엔드는 FSD 레이어(`app` → `pages` → `widgets` → `features` → `entities` → `shared`)로 나누고, slice 안은 표현(`ui`)·응용(`model`)·데이터(`api`) 3계층으로 나눈다. FSD 규칙은 Steiger로 검사한다.

Claude Code로 진행했다. 규칙은 `CLAUDE.md`와 `docs/`에 계약으로 두고, AI가 임의로 정하지 않고 사용자에게 묻도록 했다.

| 병렬 진행 | 백엔드는 따로 둔 worktree에서, 프론트엔드는 화면마다 worktree·브랜치를 나눠 서브에이전트가 동시에 만든다. 병합은 하나씩 사용자 승인을 받는다 |
| 검토 | 메인이 테스트를 돌리고, 실제 서버·브라우저에서 확인한다. 프론트엔드 PR은 만들기 전에 FSD·3계층 위반을 grep으로 찾는 구조 점검을 하고 결과를 PR 본문에 적는다 |
| PR | '논의하고 싶은 내용'에 모르는 것과 남은 한계를, '의사결정을 내린 것'에 결정과 이유를 적는다. 300줄 권장을 넘으면 이유를 적는다 |
| 병합 | 사용자가 승인하고 squash merge한다 |

| #49, #78, #80, #91 | 동시 요청 테스트만으로는 실행마다 어느 경로를 탈지 정해지지 않는다. 그래서 먼저 온 트랜잭션을 열어 둔 채 다음 요청이 잠금을 기다리는지 확인하고 커밋하는 순서 고정 테스트를 두었다. 409 변환 코드를 빼면(#49), `on conflict do nothing`을 빼면(#91) 테스트가 실패하는 것도 확인했다 |

| #51, #55 | 직접 재 보고 바꿨다. 처음 이메일 정규식은 Java와 JS의 `\s` 범위가 달랐고, 특정 입력에서 처리 시간이 길이의 제곱으로 늘었다(점 2만 개에 2.7초). 길이에 비례하는 정규식으로 바꿨다(#51). 객실 이름순은 실제 서버에서 `1001`이 `101`보다 앞에 오는 것을 보고 ICU 숫자 정렬로 바꿨다(#55, 사용자 결정) |
| #64 ~ #72 | app-admin 호텔 화면을 마친 뒤 점검해 보니 react-query를 허용 범위 밖에서 쓰는 파일이 7개였고, 폼 훅 하나가 입력·검사·요청·캐시·이동을 모두 맡았다. 기능 추가를 멈추고 규칙 문서(#64)를 먼저 고친 뒤 #65~#72에서 코드를 맞췄다(사용자 결정). 이후 프론트엔드 PR마다 구조 점검을 한다 |
| #87, #89, #91, #92 | hotel-admin 이용 화면을 만들던 중 사용자가 '이용객은 게스트 앱에서 예약하면서 등록한다'고 바로잡았다. 만들던 이용 등록 화면 코드(겹침 검사 포함)는 커밋 전에 멈춰 되돌리고, 이미 들어간 등록 요청 함수는 refactor 커밋으로 뺐다(#89). 그 뒤 문서(#87) → 백엔드(#91) → 프론트엔드(#92 hotel-admin 이용객 등록 화면 제거, 이어서 게스트 앱 예약 화면 #98) 순서로 바꿨다 |
| #93, #95, #96, #97, #98 | 게스트 앱 예약 화면(객실 선택, 예약된 기간 표시)을 만들던 중 사용자가 객실 정보를 다시 정리했다(유형으로 예약, 서버가 배정, 예약불가, 객실의 지금 이용객). 진행 중이던 객실 선택 화면을 멈추고 문서(#93) → 백엔드(#95, #97) → 프론트엔드(#96, #98) 순서로 다시 맞췄다 |
