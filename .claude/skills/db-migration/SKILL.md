# DB 마이그레이션 (Flyway)

경로는 저장소 루트 기준이다. 규칙 원문은 `backend/CLAUDE.md`의 'DB 마이그레이션 (Flyway)', '엔티티', '동시성과 충돌', '목록 조회', '테스트' 절에 있다. 문서와 다르면 문서를 따른다.

## 1. 도메인 문서 먼저

- [ ] 도메인 규칙·권한·용어는 `domain-rules` 스킬, 원본은 `docs/domain.md`. 필수 값, 유일, 범위, 이력, 삭제 여부, 기존 데이터 이전 규칙이 문서에 있는지 본다.
- [ ] 없거나 바뀌면 임의로 정하지 않고 물어 합의한 뒤 `docs/domain.md`부터 고친다(예: '객실 유형' 절의 '기존 데이터 이전').
- [ ] `docs/backend-flow.md` '3. 데이터 모델'(제약·이력·조회 방식)과 '8. 운영·관측'(기존 데이터와 새 코드의 호환성, 스키마 변경 순서, 되돌릴 방법)을 검토한다.

## 2. 파일

- [ ] 위치는 `backend/src/main/resources/db/migration/`이다.
- [ ] 이름은 `V{마지막 버전 + 1}__{설명}.sql`, 버전은 순차 정수다. 예: `V13__create_member.sql`, `V14__add_guest_member_id.sql`.
- [ ] 파일 하나에 논리적인 스키마 변경 하나(보통 그 도메인 PR의 변경 하나)를 담는다. 한 파일에 여러 도메인의 테이블을 섞지 않는다.
- [ ] 이미 적용된 파일은 고치지 않는다. 변경은 새 버전 파일로 더한다(예: `V10`이 `V9`의 배제 제약을 같은 이름으로 다시 만든다).
- [ ] 시드 데이터는 스키마(DDL)와 다른 파일로 둔다. 지금 로컬 더미 데이터는 마이그레이션이 아니라 `SeedService`다('로컬 더미 데이터' 절).
- [ ] 테스트 전용 마이그레이션은 `backend/src/test/resources/db/test-migration/`에 `V0_1`처럼 0.x 버전으로 둔다.

## 3. 테이블·컬럼

- [ ] 공통 컬럼: `id bigint generated by default as identity primary key`, `created_at timestamptz not null`, `updated_at timestamptz not null`. 엔티티는 `BaseEntity`를 상속한다.
- [ ] 동시 수정을 막는 엔티티는 `version bigint not null`(엔티티 `@Version`)을 둔다.
- [ ] 도메인 규칙을 지키는 DB 제약은 그 도메인의 마이그레이션에 함께 넣는다. 기존 예: 정리된 문자열 `check (name <> '' and name = btrim(name))`, 숫자 범위, 상태 값 목록, 초가 0인 `time`.
- [ ] 사람이 보는 이름으로 정렬하는 컬럼은 `collate natural_sort`(collation은 `V6__create_room.sql`이 만들었다). 예외는 `hotel.name`이다.
- [ ] 자주 쓰는 조회 조건과 정렬에 맞춰 인덱스를 둔다(예: `stay_room_id_check_in_date_id_idx`). 유일 제약의 인덱스가 그 조건에 쓰이면 따로 두지 않는다.
- [ ] 스키마는 Flyway로만 바꾼다. 앱은 `spring.jpa.hibernate.ddl-auto=validate`로 엔티티와 스키마를 대조하므로 엔티티·쿼리도 같은 PR에서 맞춘다.

## 4. 이름 있는 제약

- [ ] 유일·배제 제약은 이름을 붙이고 기존 이름 형식을 따른다. 예: `constraint room_type_hotel_id_name_key unique (hotel_id, name)`, 식 유일 인덱스 `guest_hotel_id_phone_digits_key`, 부분 유일 인덱스 `hotel_admin_master_key`, 배제 제약 `stay_room_id_period_excl`(`exclude using gist`, `btree_gist`). 여러 컬럼에 걸친 CHECK도 이름을 붙인 예가 있다(`stay_period_check`, `stay_amount_check`).
- [ ] 서비스가 409로 바꿀 제약은 이름을 엔티티 상수로 둔다(예: `RoomType.HOTEL_NAME_UNIQUE_CONSTRAINT`, `Stay.ROOM_PERIOD_EXCLUSION_CONSTRAINT`). `violates(제약 이름)`이 이 상수로 찾는다.
- [ ] 같은 호텔 안의 참조는 복합 외래 키로 막는 예가 있다: `room_room_type_id_hotel_id_fkey (room_type_id, hotel_id)` → `room_type (id, hotel_id)` 유일 제약.
- [ ] CHECK 제약은 이름 알파벳순으로 검사되므로, 여러 제약을 함께 어기면 먼저 보이는 제약이 다를 수 있다(저장소 테스트를 만들 때 주의, '이용' 절).

## 5. 기존 행이 있는 테이블

- [ ] not null 컬럼 추가: default로 기존 행을 채운 뒤 default를 지운다. 새 행의 값은 엔티티가 정한다(`V4__add_hotel_admin_version.sql`, `V7__add_room_status.sql`).
- [ ] 다른 테이블에서 계산해 채워야 하면 nullable로 더하고 → update로 채우고 → `set not null`과 제약을 더한다(`V11`의 `room_type_id`, `V12`의 금액).
- [ ] 데이터 이전 규칙(어떤 값을 골랐는지, 기본값)은 `docs/domain.md`에 합의한 대로 쓰고 마이그레이션에도 적는다(`V11` 첫 주석). 주석 문구는 쓰기 전에 묻는다(루트 `CLAUDE.md`).
- [ ] 이전 규칙은 `backend/CLAUDE.md`의 그 도메인 절에도 적는다(예: '객실 유형' 절의 `V11` 설명).

## 6. 테스트

- [ ] 기존 데이터를 바꾸는 마이그레이션은 마이그레이션 테스트를 둔다. 본보기: `RoomTypeMigrationTest`, `StayAmountMigrationTest`, `RoomStatusMigrationTest`.
  - `@DataJpaTest` + `@Import(TestcontainersConfiguration::class, JpaAuditingConfig::class)` + `@Transactional(propagation = Propagation.NOT_SUPPORTED)`(테스트 트랜잭션 없이).
  - 무작위 이름의 별도 스키마에 `Flyway.configure().dataSource(dataSource).schemas(schema).locations("classpath:db/migration").target(버전).cleanDisabled(false)`.
  - 이전 버전까지 `migrate()` → JDBC로 옛 모양의 행을 넣는다 → 새 버전까지 `migrate()` → 채운 값과 지운 컬럼(`information_schema.columns`)을 확인 → `finally`에서 그 스키마를 `clean()`한다.
- [ ] 새 제약은 저장소 테스트에서 `flush()`로 위반을 확인한다(롤백 기본). 서비스의 409 변환은 `backend-feature` 스킬의 테스트 항목을 따른다.
- [ ] `backend/`에서 고친 곳만 먼저 돌린다: `./gradlew test --tests '*MigrationTest'`와 관련 저장소 테스트. `docker`가 PATH에 없어 실패하면 Docker Desktop의 `resources/bin`을 PATH에 더한다(`backend-feature` 스킬 '7. 실행').
- [ ] 마지막에 전체 `./gradlew test`를 한 번 돌린다. 앱 컨텍스트가 뜨면서 `ddl-auto=validate`로 엔티티와 스키마를 대조한다.

## 7. 문서와 PR

- [ ] `backend/CLAUDE.md`의 그 도메인 절에 테이블, 제약 이름, 인덱스, 이전 규칙을 적는다.
- [ ] 커밋·브랜치·PR은 `pr-workflow` 스킬과 루트 `CLAUDE.md` '커밋 규칙', '브랜치 및 PR 규칙'. 커밋 전에 묻는다.
