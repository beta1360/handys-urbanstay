# 도메인 규칙

원본은 `docs/domain.md`다. 이 스킬은 요약과 찾아보기이고, 내용이 다르면 `docs/domain.md`가 맞다. 규칙을 서버·DB·화면에서 어떻게 지키는지는 [invariants.md](invariants.md)에 있다. 경로는 저장소 루트 기준이다.

## 1. 원칙

- `docs/domain.md`에 없는 규칙은 정하지 않는다. 문서 서두가 "여기에 없는 내용은 임의로 정하지 않고 확인한다"이고, 루트 `CLAUDE.md`가 임의 판단을 금지하며 도메인 결정은 사용자와 의논한 뒤 계획을 세우게 한다.
- 문서가 '미정'이라 한 것은 미정으로 둔다(아래 5절). 빈칸을 그럴듯한 규칙으로 채우지 않는다.
- 묻는 방식: 선택지와 권장안을 붙여 묻고, 결정은 PR 본문에 '사용자 결정'으로 남긴다(`README.md` '6. AI 활용과 검토 과정').
- 도메인이 바뀔 때의 순서
  1. 사용자에게 선택지와 권장안으로 묻고 결정을 받는다.
  2. `docs(common)` PR로 `docs/domain.md`를 먼저 고친다. API가 바뀌면 `docs/api-convention.md`도 함께.
  3. 백엔드 PR
  4. 프론트엔드 PR
  - 진행 중인 작업이 있으면 멈추고 새 규칙에 맞춘다. 예(`README.md` '진행 중 바뀐 요구와 대응'): #87 등록 주체 변경 → #91 → #92·#98, #93 유형으로 예약 → #95·#97 → #96·#98, #100 2차 개선 → #101·#102·#103·#105·#106 → #104·#107·#108·#109.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 호텔 | id로 구분한다. 이름은 같아도 되지만 이름과 주소가 모두 같으면 같은 호텔이다 |
| 객실 유형 | 호텔마다 따로 둔다. 이름, 최대 인원(1~20), 1박 요금(0~10,000,000원), 체크인·체크아웃 시각(`HH:mm`). 마스터가 만든다 |
| 객실(호실) | 한 호텔에 속하고 유형 하나를 고른다. 이름(호수), 층(선택), 소개(선택), 상태. 최대 인원·시각·요금은 유형에서 온다 |
| 객실 상태 | 공실 `VACANT`, 예약됨 `RESERVED`, 이용중 `OCCUPIED`, 정비중 `MAINTENANCE`. 운영자가 손으로 바꾼다 |
| 이용(= 예약) | 객실, 이용객, 기간, 인원, 예약 비용을 묶은 단위. 기간은 날짜 단위 반열린 구간 [체크인, 체크아웃) |
| 이용객 | 호텔마다 따로 둔 투숙객 정보(이름, 전화번호, 이메일). 회원과 연결될 수 있다 |
| 회원 | 게스트 앱(web) 계정. 앱 전체에 한 명이고 이메일이 아이디다. 운영 계정이 아니다 |
| 지금 이용 | 오늘(한국 시간)이 [체크인, 체크아웃) 안에 있는 취소하지 않은 이용. 객실 상태와 따로 정해진다 |
| 예약 비용 | 예약할 때 이용에 저장하는 1박 요금, 박 수, 기본 금액, 할인 금액(지금 0), 최종 금액 |
| 월별 정산 | 체크인 날짜가 그 달인 이용으로 계산한다. 취소 제외 최종 금액 합계·건수, 취소 건수 따로 |
| 전체 어드민 | app-admin 계정. 호텔 등록·수정, 호텔의 객실 조회, 전체 어드민 계정 관리(목록·추가·상세·이름 수정), 마스터 계정 관리, 회원 조회 |
| 호텔 마스터 | hotel-admin 계정, 호텔마다 하나. 운영자 업무 전부 + 자기 호텔 정보 수정, 유형·객실 생성·수정, 운영자 관리, 정산 |
| 호텔 운영자 | hotel-admin 계정, 한 호텔에 여럿. 객실 조회·상태 변경, 이용 조회·취소, 이용객 조회·수정 |

## 3. 핵심 불변식

[invariants.md](invariants.md)의 표(규칙 | 서버(서비스) | DB 제약 이름 | 화면)를 본다. 묶음은 예약·이용, 취소, 객실 상태, 이름과 유일, 낙관적 잠금, 범위와 조회, 정산, 계정이다. 규칙 하나를 바꾸면 그 행의 세 칸을 모두 맞춘다.

## 4. 역할과 권한

원본: `docs/domain.md` '운영 계정과 역할', `backend/CLAUDE.md` '보안', `backend/src/main/kotlin/com/marco/assignment/handys/urbanstay/common/config/SecurityConfig.kt`.

| 기능 | 전체 어드민 | 마스터 | 운영자 | 회원 | 서버가 막는 방법 |
|---|---|---|---|---|---|
| 호텔 등록(마스터 함께)·수정·검색 | O | - | - | - | `APP_ADMIN_PATTERN` → `Role.APP_ADMIN` |
| 마스터 조회·정보 수정·비밀번호 재설정 | O | - | - | - | 같음 |
| 호텔의 객실 조회(읽기 전용), 회원 조회(이용 기록 포함) | O | - | - | - | 같음 |
| 전체 어드민 계정 목록·추가·상세·이름 수정 | O | - | - | - | 같음 |
| 자기 호텔 정보 조회·수정 | - | O | 403 | - | `HOTEL_MASTER_APIS`: `GET /hotel`, `PUT /hotel`(조회도 마스터만) |
| 객실 유형 생성·수정 | - | O | 403 | - | `HOTEL_MASTER_APIS`: `POST /room-types`, `PUT /room-types/*` |
| 객실 생성·수정 | - | O | 403 | - | `HOTEL_MASTER_APIS`: `POST /rooms`, `PUT /rooms/*` |
| 월별 정산(요약·이용 로그) | - | O | 403 | - | `HOTEL_MASTER_APIS`: `GET /settlements`, `GET /settlements/stays` |
| 운영자 관리 | - | O | 403 | - | `HOTEL_MASTER_PATTERN`(`/operators/**`, `HOTEL_ADMIN_PATTERN`보다 먼저) |
| 객실 유형 목록·조회 | - | O | O | - | `HOTEL_ADMIN_PATTERN` → `Role.HOTEL_ADMIN` |
| 객실 목록·조회·상태 변경·상태 이력 | - | O | O | - | 같음. `PUT /rooms/{id}/status`는 `*`가 한 칸이라 마스터 목록에 걸리지 않는다 |
| 이용 목록·조회·취소, 이용객 목록·조회·수정 | - | O | O | - | 같음 |
| 예약, 내 이용, 내 정보, 로그아웃(web) | - | - | - | O | `MEMBER_APIS` → `Role.MEMBER`, 로그인 안 하면 401 |
| 호텔·객실 유형 조회, 회원가입·로그인(web) | 누구나 | | | | `APP_PATTERN`의 `permitAll` |
| 어드민 로그인 | 누구나 | | | | `PUBLIC_ADMIN_APIS`(`permitAll`, CSRF는 걸린다) |

- 권한 없는 계정은 403 `FORBIDDEN`, 로그인하지 않았으면 401 `UNAUTHORIZED`다. 전체 어드민 계정으로 hotel-admin API를 부르면 403, 회원 세션으로 어드민 API를 부르면 401이다(세션 속성 키가 따로다).
- 호텔 계정은 모두 `Role.HOTEL_ADMIN`, 마스터는 `Role.HOTEL_MASTER`도 받는다.
- 새 API를 더할 때: 조회는 둘 다 쓰고 변경만 마스터면, 또는 마스터만 쓰는 조회면 `HOTEL_MASTER_APIS`에 메서드+경로로 적는다. 회원 전용은 `MEMBER_APIS`, 로그인 없는 어드민 API는 `PUBLIC_ADMIN_APIS`에 적는다(접근 규칙과 API 문서가 같은 목록을 쓴다).
- 범위: 호텔 id는 세션의 `HotelAdminPrincipal.hotelId`, 회원 id는 `MemberPrincipal`에서 읽는다. 경로나 본문으로 받지 않는다. 다른 호텔의 데이터는 404다.
- 화면 규칙(`frontend/apps/hotel-admin/CLAUDE.md`)
  - '객실 유형'·'운영자'·'정산' 메뉴는 마스터에게만 보인다(`config/menu.ts`의 `masterOnly`, 판단은 `entities/account`의 `isMaster`).
  - 운영자가 마스터 전용 화면 주소로 들어오면 하위 화면 대신 `shared/ui/master-forbidden`의 권한 없음 카드('객실 목록으로')를 보여주고 그 화면의 API 요청을 보내지 않는다. `/room-types/**`·`/operators/**`는 `pages/master-access`, 정산도 같은 방식이다.
  - 객실은 `/rooms/**` 전체가 아니라 생성·수정 화면(`pages/room-create`·`pages/room-edit`)만 막고, 운영자에게 목록의 '객실 생성'·상세의 '수정' 버튼을 숨긴다.
  - 화면에서 숨겨도 서버가 403으로 막는다. 최종 판단은 서버다.
- web: 로그인하지 않았으면 예약 버튼 대신 '로그인하고 예약하기' 링크를 보여준다.

## 5. 하지 않는 것과 미정

`docs/domain.md` '미정'은 지금 없다. 2026-10-31에 정한 것(사용자 결정):

- 별도 운영 도메인(투숙 중 청소 등)은 범위 밖이다. 청소·수리는 객실 상태 '정비중'으로 다룬다.
- 전체 어드민 계정의 이름 변경은 세션을 끊지 않는다.
- 게스트 앱 노출 설정은 두지 않는다. 호텔 목록에서 객실이 있는 호텔을 앞에, 없는 호텔을 뒤에 비활성으로 둔다.

다루지 않기로 한 것(`docs/domain.md`, `README.md` '하지 않은 것')

- 객실 상태 자동 변경. 예외는 취소 때 예약됨 → 공실 하나다
- 이용 수정. 취소하고 다시 예약한다
- 결제, 할인 규칙. 할인 금액은 0이고 자리만 있다
- 게스트의 예약 취소. 취소는 hotel-admin에서 한다
- 회원 정보 수정·비밀번호 변경·탈퇴, 호텔 계정 본인 비밀번호 변경
- 호텔·객실 유형·객실·이용객 삭제. 운영자 계정은 지우지 않고 비활성화한다
- 객실 배정 규칙(청소 상태, 층 등). 이름순 첫 빈 객실이다
- 체크인·체크아웃 시각까지 반영한 '지금 이용' 판정. 날짜 단위다

알려진 한계(`README.md` '남은 한계'): 이용객은 전화번호가 같으면 같은 사람으로 본다(#102). 지금 이용과 객실 상태는 따로라 '공실'인데 지금 이용객이 보일 수 있다(#96).

이 목록의 무엇을 하자는 요청은 새 도메인 결정이다. 1절의 순서로 묻는다.

## 6. 도메인 변경 전 체크리스트

- [ ] `docs/domain.md`의 어느 절이 바뀌는가? 문서에 없거나 미정이면 멈추고 선택지와 권장안으로 묻는다.
- [ ] [invariants.md](invariants.md)의 어느 행이 닿는가? 서버(서비스)·DB 제약·화면 세 칸을 모두 맞추는가?
- [ ] 4절 권한 표의 어느 행이 닿는가? `SecurityConfig`의 목록·경로 규칙과 화면(메뉴, 버튼, 권한 없음 카드)을 함께 바꾸는가?
- [ ] 마이그레이션이 필요한가? 적용된 파일은 고치지 않고 새 버전을 더한다(지금 V14까지). 규칙을 지키는 DB 제약은 그 도메인 마이그레이션에 이름을 붙여 넣고, 이름은 엔티티 상수로 둔다. 기존 데이터를 옮기면 그 규칙을 마이그레이션에 적는다(`backend/CLAUDE.md` 'DB 마이그레이션', '동시성과 충돌').
- [ ] 동시 요청에서도 지켜지는가? 사전 확인만으로는 부족하다. 유일 제약, 배제 제약, 비관적 잠금, 낙관적 잠금, 조건부 UPDATE, `on conflict do nothing` 중 무엇으로 막는지 정한다.
- [ ] 테스트: 동시 요청과 순서를 고정한 경로 테스트, 마스터 전용 API는 운영자 principal로 403과 바뀌지 않음, 두 역할이 쓰는 API는 `@EnumSource(HotelAdminRole::class)`, 오늘 규칙은 `FixedClockConfiguration`.
- [ ] 날짜 기준: 서버는 `Clock` 빈(Asia/Seoul), 화면은 한국 날짜(`getKoreanToday`)다.
- [ ] PR 순서: `docs(common)` → backend → frontend. 한 PR에 섞지 않는다.
